## The task

`@nera-static/validate` produces every finding that `nera validate` and
`nera check` print — and, since `@nera-static/nera` 1.9.0, every finding an AI
agent reads from `nera validate --json` / `nera check --json`. An agent gets one
finding at a time, `{ file, line, severity, rule, message }`, with no README at
hand. Review **every** message this package can emit and make each one
actionable on its own: it says **what** is wrong, **where** (the file and line
are in the result; the message names the offending value — the layout name, the
include target, the config key, the element), and **what to do** about it (a
concrete fix, or the way to silence it on purpose when that is legitimate). Many
messages already do this — mostly the output-pass (`a11y-*`, `privacy-*`,
`legal-*`) ones; the source-pass ones in `index.js` and `src/pug-refs.js` are the
weakest. Improve the ones that fall short, leave good ones alone, and pin the
result with tests.

## Facts you need (the current truth, 2026-10-12)

### The contract — what must NOT change (from `.claude/issue-conventions.md` and the maintainer)

- The result shape `{ file, line, severity, rule, message }` (output findings
  add `source`, collapsed ones add `files`) and **every `rule` id** are a
  contract: the CLI, `nera check`, the Nera Pro platform and `ignore:` in
  `config/validate.yaml` key on them. Renaming or removing a rule id is a
  **major** release; this issue must not do it. Do not change any `severity`,
  any default `level`, which findings are produced, or `file`/`line` values —
  **only the `message` strings** (and the `❌` error text of thrown errors, see
  below). A reworded message is a **patch** release.
- **Keep each message's existing opening words** and extend after them (e.g.
  `include/extends target "x" does not resolve — …`). The Nera Pro platform has
  a test that looks for `does not resolve` in the `include-unresolved` message,
  and people grep for the old wording. If an opening is genuinely misleading,
  you may change it, but list it under "Review hints" with the reason.
- **Output-pass messages must stay page-independent.** `src/output.js#collapse`
  merges findings with the same `rule` + `severity` + `message` across files
  (a layout problem repeats on every page) and appends
  `(on N pages, e.g. …)`. If you put a per-page value (the page path, its URL)
  into an output-rule message, identical layout findings stop collapsing and a
  50-page site prints 50 lines. Element descriptions via `describe(el, …)` are
  fine — they are the same on every page that shares the layout.
- Messages are English, lower-case start, no trailing period, inline code in
  backticks, one line (no `\n`), and the existing ` — ` (space, em dash, space)
  separator between "what" and "what to do". Keep the WCAG/DSGVO/DDG references
  the output messages carry. Keep them reasonably short: one sentence of what,
  one of what to do; no essays.
- Library functions return results; only `bin/nera-validate.js` prints.

### Messages that come from `@nera-static/core` (a sibling repo, not this one)

Two findings in `validateSite` (`index.js`) pass through text from core:

- `yaml-parse` on `config/app.yaml`: `config could not be parsed: ${model.appConfigError}` —
  `appConfigError` is the `yaml` package's `err.message` (multi-line, with a
  code frame). Note: the page-frontmatter `yaml-parse` already uses only the
  first line (`err.message.split('\n')[0]`); the app.yaml one does not.
- `theme-unresolved`: `message: model.themeError` — core's thrown text, one of:
  - `theme: "<spec>" resolved to <root>, but <viewsRoot> does not exist`
  - `theme: "<spec>" — package <pkg> is not installed. Run: npm install <pkg>`
  - `theme "<name>" requires Nera generator <range>, but this generator is <version>. Update the generator (nera update) or install a theme version compatible with <version>.`

  (There may be other `throw`s in core's `src/theme.js`; you can read it in
  `node_modules/@nera-static/core/src/theme.js` after `npm ci`.)

Do **not** try to change core. Improve what you can **in this repo**: e.g. keep
only the first line of `appConfigError` and add a what-to-do; for
`theme-unresolved`, add a what-to-do only where core's text has none (the first
variant), without duplicating core's own instruction. If core's wording itself
should change, put that under "Carry-forwards" with the exact suggested text —
the maintainer files it for `@nera-static/core`.

### Thrown errors

- `validateOutput` throws `no built HTML in <dir>/ — run \`nera build\` first`
  when there is no output. The CLI turns a throw into
  `{ "ok": false, "error": "<message>", "results": [] }` in `--json` mode and a
  `❌ <message>` line otherwise, so thrown texts are agent-facing too: review
  them by the same standard (that one is already fine).

### Where the messages live (inventory starting point, not necessarily complete)

- `index.js` — `theme-shadowed`, `yaml-parse` (app.yaml, frontmatter),
  `theme-unresolved`, `layout-missing`, `layout-unresolved`.
- `src/pug-refs.js` — `include-unresolved`.
- `src/config.js` — `yaml-parse` (validate.yaml), `config-invalid` (`ignore`).
- `src/output.js` — `config-invalid` (`rules`, `legal`, `privacy`), the

- `src/format.js` — `OUTPUT_NOTE` (a footer, not a finding; leave it unless it is wrong).

Specific weaknesses the maintainer already noticed (check them, do not stop there):

- `layout-missing`: `page has no \`layout\` — the build skips it silently` says
  what, not what to do. The fix is either adding `layout: <name>` to the
  frontmatter (naming where layouts live — the site's `views/` folder, or the
  theme's — and, if cheaply knowable, an example), or, for content fragments
  and drafts that have no layout on purpose, `ignore: { layout-missing: [<path>] }`
  in `config/validate.yaml`.
- `layout-unresolved`: `layout "x" not found in views or theme` — say where it
  looked (the site's views folder, and the theme's when there is one, as
  site-relative paths if you can get them from `resolveSiteModel`'s `roots` /
  `folders`), and what to do (create the file, or fix the name).
- `include-unresolved`: `include/extends target "x" does not resolve` — say
  where it was looked up and what to do.
- `yaml-parse` (all three places): say what to do (fix the YAML at that line;
  name the usual culprit if the parser's first line does not, e.g. a `: ` in an
  unquoted value — quote the value).
- `privacy-third-party` (output-rules.js ~150–160): check that the "what to do"
  is complete for both the known-service and the generic branch.
