## Plan

says **what** is wrong, **where** (file/line in the result, the offending value
in the text) and **what to do**. Only `message` strings change — no rule id,
severity, default level, `file` or `line`. Openings stay; the fix is appended
after the existing ` — ` (or `; `), in the house style "what — why; what to do
(law)". Output-pass messages stay page-independent (no page path or URL).

## Decisions

- **Message form.** `<what> — <why>; <what to do> (<law/WCAG ref>)`. The fix starts with an imperative, either right after the first ` — ` or after a later `; `. A legitimate way to silence the finding on purpose, when there is one, joins the fix with `, or …`.
- **The table test pins that form for every source-pass rule.** The fix must match `/ — (?:.*?; )?(?:add|create|fix|quote|delete|remove|use|write|put|list|set|run|install|update)\b/`. The message must also be one line, start lower-case or with a backtick, and have no trailing period. Add a verb to the list only when a new message really needs it.
- **`yaml-parse` uses one hint for all three files.** It keeps the parser's first line without its trailing `:`, then adds `— fix the YAML at that line: quote a value that contains `: ` or ` #` or starts with `[`, `{`, `*`, `&` or `@`, and close any open bracket or quote`. For frontmatter, the parser's `at line N` is moved to the file line, so the text agrees with `line`.
- **`layout-missing` names the most-used layout as its example.** It picks the layout most pages use, counting only layouts that resolve (first seen on a tie). Without one it says "a `layout:` key". It names the views folders and gives the exact `ignore: { layout-missing: [<page>] }` entry for `config/validate.yaml`. No new I/O: the example comes from pages already walked.
- **"looked for" lists exactly the files the validator checked, site-relative, in order.** "create" names the site's own copy, which works with or without a theme and also overrides a theme. It says "it" when only one path was checked. For an extensionless value, the validator checks the bare path in each root, then `<site views>/<value>.pug`, and the message shows all of them.
- **`theme-unresolved`: this repo adds a fix only to core's "does not exist" variant.** The variant is detected by the text ending in ` does not exist`. The other variants already carry core's own instruction and pass through unchanged.
- **`config-invalid` shows the correct YAML.** The form is `<key> must … — write it as `<correct YAML>`; ignoring it` (or `put … under it`). The `legal.<kind>` examples are per kind (`/de/impressum.html`, `/de/datenschutz.html`).
- **Output-pass fixes use only element values or static text.** Collapsing is therefore unchanged. Legal and privacy fixes stay hints ("consider", "confirm", "cite … instead"), not verdicts.
- **`privacy-third-party`, known hosts:** `<note>, or list the host under `privacy.allowed_hosts` in config/validate.yaml once it is accounted for`. Generic hosts: `self-host the resource, or name the host in the privacy policy and list the host under …`. The Google Analytics / Tag Manager note gains "load it only after the visitor agrees".

## Carry-forwards

- **`src/pug-refs.js:12-19` (`resolveTarget`) wrongly reports a theme-only extensionless include as unresolved.** Pug appends `.pug` while lexing, before it calls the resolver. `resolveTarget` resolves the raw target and appends `.pug` only to the resolver's fallback. So `include ../partials/x`, where `x.pug` exists only in the theme, is reported unresolved although the build finds it. Not fixed: it changes which findings are produced. The new message lists the files actually checked, so it is honest about it.
- **`index.js` `resolveLayout` has the same shape for an extensionless `layout`.** It tries the bare value in every root and `.pug` only in the site's views. I did not verify what the build does with an extensionless layout: `render.js` calls `resolveEntry` and then compiles that path. Worth one decision for both.
