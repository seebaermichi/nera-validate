# Result — Review all messages: what, where, what to do (01a1260d-8eb2-71a9-8688-5a7ff8f4b449)

## Plan

Goal: every message (and thrown error text) `@nera-static/validate` can emit
says **what** is wrong, **where** (file/line in the result, the offending value
in the text) and **what to do**. Only `message` strings change — no rule id,
severity, default level, `file` or `line`. Openings stay; the fix is appended
after the existing ` — ` (or `; `), in the house style "what — why; what to do
(law)". Output-pass messages stay page-independent (no page path or URL).

Steps:

1. This inventory (commit 1).
2. Source pass (`index.js`, `src/pug-refs.js`, `src/config.js`): one shared
   YAML hint for all three `yaml-parse` findings (first parser line only, no
   trailing `:`; frontmatter positions rewritten to the file line);
   `theme-unresolved` gets a fix only for core's "views does not exist" variant;
   `layout-missing` names how to add a layout (with the site's most-used layout
   as the example, from the pages already walked — no new I/O) and how to
   silence it; `layout-unresolved` and `include-unresolved` name the
   site-relative paths that were looked up (from `model.roots`) and say "create
   the file or fix the name/path"; `config-invalid` for `ignore` shows the
   correct form.
3. Output pass (`src/output.js` config, `src/output-rules.js`): add a short
   fix to the rules that only state the problem; leave the ones that already
   have one.
4. Tests: a `toContain` assertion on the new fix part of each changed message;
   one table test in `test/validate.test.js` triggering every source-pass rule
   and requiring a what-to-do clause; update only assertions that pinned old
   whole-string wording.
5. README: update the quoted `layout-unresolved` example message.
